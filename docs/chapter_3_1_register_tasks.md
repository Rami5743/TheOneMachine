# פרק 3.1 — משימות הזיכרון (Register4, Register) — מפרט למימוש

> סטטוס: **המפרט תועד, המימוש בתהליך.** הדרישות והרמזים כבר מקודדים ב-`MEMORY_TASKS`
> (js/app-data.js). כרגע הקשה על משימה בפתק מציגה "המשך יבוא..." עד שסביבת הבנייה
> והבודק הסדרתי יוקמו.

## סוג המשימה: כרטיס מתוזמן (סדרתי)

בניגוד לכל המשימות עד כה (קומבינטוריות, נבדקות בטבלת אמת), המשימות האלה הן
**מתוזמנות/סדרתיות**:

- **סרגל הכלים בבנייה** מציג את **כל הכלים מהשלבים הקודמים** בתוספת **נעצים** ו-**FF**.
- אפשר לחבר מעגלים (לולאות), אבל **בכל לולאה חייב להיות לפחות FF אחד** (כמו בשולחן
  המתוזמן של 3.1).
- **רכיבים קומבינטוריים מיידיים**, **FF לוקח קלוק אחד** (תקף רקורסיבית).
- **שעון רץ ב-2 הרץ** בזמן הבנייה.

## הבדיקה: התנהגות זיכרון (לא טבלת אמת)

בבדיקת כרטיס בודקים את **התנהגות הזיכרון** שלו: אין טבלת אמת. במקום זה משנים את
הקלט מספר פעמים לאורך כמה קלוקים ובודקים שהפלט תקין **בהתחשב בהיסטוריה**.

רצף בדיקה מוצע ל-Register4/Register (control = כניסת הבקרה, data = בס הכניסה):
1. control=1, data=A → אחרי קלוק היציאה = A (טעינה).
2. control=0, data=B → היציאה נשארת A (נעילה/שמירה).
3. control=0, data=C → היציאה עדיין A.
4. control=1, data=C → אחרי קלוק היציאה = C (טעינה חדשה).
5. control=0, data=A → היציאה נשארת C.
(לבחור כמה ערכים אקראיים/קבועים שמכסים גם "טעינה" וגם "שמירה".)

## Register4

- כניסות: בס ברוחב 4 (data) + כניסת בקרה בודדת (control). יציאה: בס ברוחב 4.
- בתוכו 4 פליפ-פלופים ששומרים 4 ביטים. מוציא את המידע השמור.
- control=0 → המידע לא משתנה; control=1 → המידע משתנה לפי הכניסה.
- **הכרטיס מופיע כבר עם 4 הפליפ-פלופים בפנים** — הלומד מחווט את המפצלים והבקרה.

רמזים:
1. אפשר תמיד להתחיל מלפצל את הכניסה והיציאה.
2. להשאיר את כניסת הבקרה לסוף; קודם לטפל בשאר.
3. כתיבה (שינוי מה שנשמר) קורית בכל הכרטיס בו-זמנית → כניסת הבקרה של כל
   הפליפ-פלופים חייבת להיות אותו הדבר.

פתרון: באחריות קלוד (split data[4]→4 ביטים→4 data-in של ה-FF; control→4 control-in;
4 out של ה-FF→combine→out[4]).

## Register

- כניסות: בס ברוחב 16 (data) + בקרה בודדת. יציאה: בס ברוחב 16. 16 פליפ-פלופים.
- אותה התנהגות כמו Register4.

רמזים:
1. אפשר להשתמש ב-Register4, או לבנות כמו Register4 רק עם 16 פליפ-פלופים.
2. כניסת הבקרה של כל הפליפ-פלופים חייבת להיות אותו הדבר.

פתרון: באחריות קלוד.

## שלבי מימוש מתוכננים

1. הגדרת טיפוסי מסגרת `register4Frame` / `registerFrame` (bus[4]/[16] data משמאל,
   בקרה בודדת מלמעלה, bus[4]/[16] out מימין) עם ה-FF-ים מוצבים בפנים (fixed).
2. `openMemoryTaskWorkspace` — סביבת בנייה מתוזמנת (clocked=true, שעון 2Hz),
   סרגל = כל הכלים + נעצים + FF, מסגרת + FF-ים + מקור בדיקה.
3. פאנל דרישות + רמזים (reuse של מנגנון הדרישות/רמזים הקיים; הטקסט כבר ב-MEMORY_TASKS).
4. בודק סדרתי: להריץ את רצף הבדיקה למעלה על המנוע המתוזמן ולוודא פלט מול היסטוריה.
5. הליכי פתרון (solution walkthroughs) ל-Register4 ו-Register.
6. חיבור `handleMemoryNoteTask` לפתיחת הבנייה במקום "המשך יבוא"; החזרה לשולחן 3.1.
